> 📅 **최종 확인**: 2026-11-22

지식그래프가 커지면 서로 모순되는 사실이 조금씩 섞여 들어옵니다. 사람이 일일이 찾기는 어렵기 때문에, **모순 패턴을 SPARQL 질의로 만들어 두고 정기적으로 실행**합니다.

## 요약

- 자주 생기는 모순 유형을 **검사 질의**로 만들어 둡니다.
- 새 데이터를 넣을 때와 정기 점검 때 **자동으로 실행**합니다.
- 형식 오류는 SHACL(02-4), 여러 사실 사이의 모순은 SPARQL 검사가 잘 잡습니다.

## 자주 생기는 모순 유형

| 유형 | 예 | 원인 |
|---|---|---|
| 클래스 충돌 | D화학이 회사이면서 "근무한다"의 주어(사람) | LLM이 "D화학 출신 임원"을 잘못 해석 |
| 자기 참조 | B소재가 B소재에 공급 | 동명 회사·자회사 혼동 |
| 개수 위반 | C전자의 설립연도가 두 개 | 서로 다른 출처의 값이 함께 들어옴 |
| 순환 | A가 B에, B가 A에 공급 | 실제 거래일 수도 있지만 확인 필요 |

## 코드: 모순 찾기

검사를 위해 예제 데이터에 **일부러 잘못된 사실 세 가지**를 추가한 뒤 네 가지 검사를 실행합니다. 전체 코드는 `code/10_consistency.py`입니다.

```python
g.add((EX.DChem, EX.worksFor, EX.AElec))          # 회사가 회사에 '근무'
g.add((EX.BMat, EX.suppliesTo, EX.BMat))          # 자기 자신에게 공급
g.add((EX.CElec, EX.foundedYear, Literal(2015)))  # 설립연도가 두 개
```

검사 질의 예시 (클래스 충돌):

```sparql
SELECT DISTINCT ?name WHERE {
  ?x ex:worksFor ?any .               # 근무한다의 주어 → 사람이어야 함
  ?x a/rdfs:subClassOf* ex:Company .  # 그런데 회사이기도 함
  ?x rdfs:label ?name .
}
```

**실행 결과**

```text
[❌] 사람과 회사로 동시에 쓰인 개체: D화학
[❌] 자기 자신과의 관계: B소재
[❌] 값이 하나여야 하는데 여러 개: C전자 2
[❌] 공급 관계의 순환 (A→…→A): B소재
```

추가한 세 가지 오류를 모두 찾아냈습니다. 마지막 순환 검사도 B소재를 찾았는데, 이는 자기 자신에게 공급하는 관계가 **가장 짧은 순환**이기 때문입니다. 이처럼 한 오류가 여러 검사에 동시에 걸리기도 합니다.

## OWL 추론기로 찾는 모순

`owl:disjointWith`(사람과 회사는 겹칠 수 없음)를 온톨로지에 선언하면, OWL 추론기가 클래스 충돌을 **논리적 모순**으로 찾아 줍니다. 규칙이 복잡해질수록 추론기가 유용하지만, 실행 시간이 길어질 수 있으므로 자주 쓰는 검사는 SPARQL로 따로 만들어 두는 것이 좋습니다.
